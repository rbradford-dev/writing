What Building a Multi-Agent Threat-Intel System Taught Me About CISA KEV

I spent this summer building a multi-agent cybersecurity system called CyberSentinel — a Claude-orchestrated platform where specialized subagents handle vulnerability triage, threat-intel enrichment, log anomaly detection, and incident reporting. It queries NVD, CISA KEV, AlienVault OTX, and AbuseIPDB, persists findings to SQLite, and serves a real-time dashboard. No LangChain; custom orchestration directly on the Anthropic SDK.

The part I expected to be easy was the CISA Known Exploited Vulnerabilities catalog. It’s a JSON file. You download it, you check whether a CVE is in it. That’s the whole feature.

That assumption was wrong in three specific ways, and each one taught me something about how exploitation data actually behaves in a triage pipeline.

1. KEV membership is a better priority signal than CVSS, and the ordering matters

The naive way to triage vulnerabilities is to sort by CVSS score and work down the list. Everyone starts here. It’s wrong, and KEV is the reason.

CVSS answers “how bad would this be if someone exploited it?” KEV answers “is someone exploiting it?” Those are different questions, and the second one is far more useful for deciding what to patch on Monday morning.

When I wrote the triage rules for the vulnerability agent, the ordering ended up looking like this:

  • KEV + internet-facing → P1, 24-hour deadline, patch immediately
  • CVSS ≥ 9.0 → P1 unless there are documented compensating controls
  • CVSS ≥ 7.0 and in KEV → P1
  • CVSS ≥ 7.0 → P2, 7 days
  • CVSS ≥ 4.0 → P3, 30 days
  • Below 4.0 → P4, 90 days

Notice that the first rule doesn’t mention CVSS at all. A KEV-listed vulnerability on an internet-facing asset is a P1 whether its CVSS is 9.8 or 6.5, because the score is a hypothesis about severity and KEV membership is an observation about reality. A medium-severity bug that attackers are actively using is a bigger problem than a critical-severity bug that nobody has weaponized.

Two real PAN-OS vulnerabilities make the point better than the abstraction does. CVE-2025-0111 is an authenticated file-read flaw in the PAN-OS management interface. NVD scores it 6.5, MEDIUM. It is in the KEV catalog, added 2025-02-20, with a federal remediation deadline of 2025-03-13 — twenty-one days. CVE-2026-0263 is a buffer overflow in PAN-OS IKEv2 processing that lets an unauthenticated attacker execute arbitrary code on the firewall. NVD scores it 9.8, CRITICAL. It is not in KEV.

A CVSS-sorted queue puts the 9.8 first and the 6.5 twenty rows down. My rules invert that: the 6.5 is P1 with a 24-hour clock, and the 9.8 waits behind it. That looks wrong for about five seconds, and then it looks obviously right — CISA put the 6.5 on a legally binding remediation timeline because it is being exploited against real networks, and nobody has put the 9.8 on any list because as far as anyone can observe, no one is using it. Same vendor, same product, one attacker-validated and one not. Worth noting that the scoring is not unanimous: Palo Alto’s own PSIRT rates both issues at roughly 7.1 and 7.2 under CVSS v4.0, so the wide gap here is specific to NVD’s v3.1 scoring rather than a universal verdict. The 3.3-point CVSS gap is a statement about what an attacker could achieve; the KEV listing is a statement about what they are doing.

The rules are ordered, not weighted, and that’s deliberate. I tried a weighted scoring model first — multiply CVSS by a KEV coefficient, add an exposure term, sort descending. It produced defensible-looking numbers that were impossible to explain to a human. When someone asks “why is this a P1,” the answer needs to be a sentence, not a formula. Ordered rules give you that sentence for free: it’s in KEV and it’s internet-facing.

2. The catalog is a feed, not a file, and your cache design is a security decision

My first implementation fetched the KEV JSON on every run. That works fine until you’re making twenty agent calls in a session and you’ve turned a public-good feed into your personal DDoS target.

So I added caching with a TTL. Then I hit the interesting case: what happens when the fetch fails and the cache is expired?

There are two defensible answers and they are not equally correct.

You can fail closed — return nothing, report the data source as unavailable. This is honest. It’s also useless, because now your triage runs with no exploitation data at all and silently downgrades every KEV vulnerability to “just a CVSS score.”

Or you can fall back to the stale cache and say so loudly. That’s what I ended up doing: try the network, and if it fails, load the cache ignoring the TTL, log a warning that the data is stale, and continue. A KEV catalog from last week is dramatically better than no KEV catalog, because the overwhelming majority of entries didn’t change. The failure mode of stale data is missing the newest additions. The failure mode of no data is treating every actively-exploited vulnerability as theoretical.

The general principle I took from this: when a data source degrades, ask what the silent failure looks like. Missing enrichment data usually doesn’t announce itself — it just quietly makes your output less correct while it keeps looking exactly as confident.

3. Exploitation data has structure that a boolean throws away

The obvious API for KEV is is_exploited(cve_id) -> bool. I wrote that. It’s an O(1) set membership check and it’s the function I call most.

But building only that function throws away most of the catalog’s value. Each KEV entry carries the date it was added, the vendor and product, a required remediation action, a due date, and — the field I underused for weeks — knownRansomwareCampaignUse.

That last field turns out to be the single most useful thing in the feed for a healthcare context. “This CVE is exploited” and “this CVE is exploited by ransomware crews” are wildly different escalations when the asset in question supports patient care. Ransomware against a hospital isn’t a data-confidentiality problem, it’s a care-delivery problem: diverted ambulances, downtime procedures, delayed imaging.

I ended up building three more accessors alongside the boolean:

  • the full entry for a CVE, so triage can cite the required action and due date rather than inventing one
  • recent additions within N days, which is how you answer “what changed this week” without diffing the whole catalog
  • ransomware-associated entries, filtered on that campaign-use field. That filter is narrower than you’d expect: roughly one in five KEV entries are associated with known ransomware campaigns. Which is the point. It’s a small, specific list of things known to be used by crews whose business model is halting operations.

The recent-additions query is the one that changed how I think about the feed. A KEV addition is a state change in the world — CISA is telling you that something previously theoretical is now happening. That’s a triggerable event, not a lookup. The same data supports both a “is this bad” question and a “what just became bad” question, and only the second one lets you get ahead of anything.

The thing I’d tell myself at the start

I treated KEV as an enrichment field — a flag to hang off a CVE record I’d already retrieved from NVD. Something to make the output look more complete.

It’s better understood as the priority axis, with CVSS as the tiebreaker. NVD tells you what a vulnerability is. KEV tells you whether it’s your problem this week. Once I inverted that relationship, the triage output stopped reading like a vulnerability scanner and started reading like advice.

There’s a broader lesson in here about building with AI agents, too. The temptation with an LLM orchestrator is to hand the model everything and let it reason its way to a priority. I tried that. It produced fluent, plausible, inconsistent results — the same CVE would land P1 or P2 depending on what else was in the batch. Encoding the priority rules explicitly in the system prompt, in a fixed order, and letting the model do the contextual work — is this device internet-facing, does this touch patient care — was the fix. Deterministic where determinism is available; judgment where it isn’t.

Which is roughly the same lesson as the KEV one. Use the hard signal where you have a hard signal.

CyberSentinel is a personal project — a multi-agent cybersecurity platform built on the Anthropic SDK with FastAPI, SSE, and SQLite. 165 passing tests, four specialized agents, seven threat-intel integrations.
