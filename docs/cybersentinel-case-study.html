CyberSentinel: a multi-agent threat-intel triage tool (case study)

Robert Bradford · personal project · source code not public

The problem

Vulnerability triage usually starts with a list of CVEs sorted by CVSS score. That ordering tells you how bad a bug could be. It says nothing about whether anyone is exploiting it right now, and checking that by hand means bouncing between several public feeds for every CVE. I wanted a tool that pulls those sources together, applies explicit priority rules, and explains why each item landed where it did.

Architecture

CyberSentinel is a Python application with a custom orchestrator written directly on the Anthropic SDK. I did not use LangChain.

  • Orchestrator and router. A query comes in, the router decides which specialist agents need to run, and the orchestrator collects their results into one answer.
  • Four specialist agents. One handles vulnerability triage, one does threat-intel enrichment, one analyzes logs for anomalies, and one writes the report. Each agent returns a structured result object, so the orchestrator never has to parse free text from another agent.
  • Public data sources. Integrations include NVD, CISA KEV, AlienVault OTX, and AbuseIPDB, plus optional enrichment clients that switch themselves off with a logged warning when no API key is set.
  • Storage. Findings persist to SQLite through a small repository layer with migrations.
  • Dashboard. FastAPI serves the UI. Agent progress streams to the browser over Server-Sent Events (SSE), and Chart.js draws the trend and severity panels. All front-end dependencies are vendored, so the dashboard makes no CDN calls at runtime.
  • Cost tracking and retries. Each query records token cost, and LLM calls retry with exponential backoff.

Two design choices mattered most. First, the priority rules run in a fixed order, and the first match wins. A KEV-listed CVE on an internet-facing asset is P1 regardless of its CVSS score, and CVSS breaks ties further down. The model handles the contextual questions, like whether an asset is exposed. Second, when the KEV feed can’t be fetched, the client falls back to the last cached copy and logs that the data is stale. Running with no exploitation data at all would quietly make every result less correct. I wrote about both choices in more detail at https://rbradford-dev.github.io/writing/cisa-kev-lessons.html.

Mock demo

CyberSentinel has a mock mode that swaps the live LLM for a deterministic stand-in with a configurable delay. That lets me demo the whole pipeline with no API keys and no real data.

In a typical demo run I load a synthetic incident log written for the demo. It describes a fictional network where an account gets brute-forced, the attacker moves laterally, data leaves the network, and a host starts beaconing to a command-and-control server. I type a question into the run terminal on the dashboard. The router sends the log to the log-analysis agent and any indicators to the threat-intel agent. Agent status updates stream into the activity panel as each step finishes. The report agent then writes an incident summary, the findings land in SQLite, and the dashboard charts update. Every host, account, and address in the log is made up.

Testing

  • 165 passing tests at the v1.0.0 milestone. That is the count I have stated publicly for the mock-mode suite at that version.
  • Tests use pytest and cover agent handoffs, upstream API failure modes, and the dashboard’s read endpoints. Some live-LLM tests expect a connected model and fail when the suite runs without one.

Limitations

  • The repository is private, so nobody can check this write-up against the code yet.
  • Live-LLM tests still fail without a live model, and live mode has needed configuration fixes when I last checked.
  • LLM output varies between runs. Putting the priority rules in a fixed order in the prompt made results much more consistent, but I have not measured triage accuracy against a labeled set of CVEs.
  • The stale-cache fallback for KEV can miss the newest catalog additions until the feed comes back.
  • It is a personal project. It has not been deployed as a production service.
